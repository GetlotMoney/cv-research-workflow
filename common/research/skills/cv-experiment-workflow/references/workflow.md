# 当前科研流程

本文件展开科研工作流 V1.0 的唯一操作顺序。日常对象只有个人工作区、GZSL 仓库、Framework、实验、Run 和人工确认。

## 1. 通用模板

安装后系统可以在没有个人工作区时启动。此时只允许查看环境、六方向状态和使用说明，不创建任何个人目录。

## 2. 个人工作区

用户主动实例化后，系统在 `users/<slug>/` 建立个人目录。激活后重新启动服务，页面才读取该工作区。

个人工作区保存：

- 方向仓库；
- 外来代码收件目录；
- 科研材料；
- 科研交付；
- 本地运行文件。

## 3. GZSL 仓库

页面只允许选择状态为 `ready` 的 GZSL。创建仓库时系统：

1. 复制当前 GZSL 方向材料；
2. 初始化 Git；
3. 建立稳定基础 Framework；
4. 创建基础提交和稳定 Tag；
5. 写入仓库索引。

另外五个方向在复制文件前就必须拒绝。

## 4. Framework

Framework 是一套完整可训练、评估和推理的代码，不依赖 Idea 才存在。一个仓库可以登记多个 Framework：

- 系统自带的稳定基础 Framework；
- 通过标准化检查的外来 Framework；
- 由成功创新晋级的子 Framework。

只有这三类稳定 Framework 可以打 Tag。

## 5. 四类实验

### 复现

开始前固定目标结果、允许误差、数据划分、代码身份和评估规则。复现只回答“相同条件下能否得到相符结果”。

### 调参

只改变参数，不改变代码行为。开始前固定搜索范围、选择方法、预算和停止条件。

### 消融

固定要关闭或替换的组成部分、启用侧结果、关闭行为和比较指标。消融不产生子 Framework。

### 创新

必须绑定 Idea，写清问题、机制、可验证假设、真实基线和最低提升要求。创新结论与 Run 是否可信分别判断：Run 可以可信，但创新仍可能不成立。

## 6. 分支与 Worktree

每个实验建立独立分支和 Worktree。所有代码修改、数据登记和 Run 都在该 Worktree 内完成，避免不同实验相互污染。

普通 Run 不打 Tag。只有创新被接受、人工确认并提交后，才能晋级成稳定子 Framework。

## 7. 数据登记

真实数据留在用户指定位置。登记时保存：

- 数据集名称和版本；
- 来源地址与许可证；
- 文件 SHA-256；
- 数据内容清单；
- 类别和划分信息。

数据登记失败时必须清理未完成记录，允许用户修正后使用同一短名重试。

## 8. GPU Run

先运行小规模 GPU debug，再运行正式 evidence。二者必须使用相同配置和随机种子。

一次 Run 固定完成：

```text
train → evaluate → infer → 保存日志、指标和产物哈希
```

正式 Run 必须由中央可信 CUDA 探针执行真实张量计算。外来代码不能自己写一个“CUDA=true”文件冒充通过。

## 9. 人工确认

确认前检查代码提交、工作树状态、数据身份、配置、随机种子、S/U/H、日志和产物。没有人工确认的 Run 不能成为正式科研结果。

创新还要单独记录接受或拒绝结论；拒绝创新不等于删除 Run。

## 10. 外来 Framework

外来代码按以下顺序处理：

1. 放入个人 `inbox`。
2. 人工检查来源、许可证和将要执行的脚本。
3. 扫描数据、模型、损失、训练、评估、推理、指标和配置入口。
4. 修正组件与文件的对应关系，一个组件可以对应多个文件。
5. 生成受控标准化草稿。
6. 明确信任后运行标准测试和中央 CUDA 检查。
7. 在临时 Git 快照中删除旧结果并重跑等价命令。
8. 两名不同复核人确认相同数据、划分和 S/U/H 后，登记为稳定 Framework。

信任确认不是操作系统沙箱。来源不明的代码不要执行。

## 11. 当前停止位置

当前科研流程在“Run 已人工确认”处完成。只有用户以后主动开始独立论文阶段时，才另行准备科研交付材料。
